# AsterCode v0.1 验收矩阵

本文把“像 Claude Code 的本地编程 Agent”收敛成一组可重复、可观察、可审计的验收场景。矩阵是 v0.1 的产品边界，不把真实 Provider、SSH、外网浏览器或 GUI 的未验证状态写成通过。

## 1. 通过定义

v0.1 的核心闭环是：

`只读分析 → 多轮对话 → 精确审批 → 最小修改 → 失败测试 → 修复 → diff/审计 → 可恢复`

每个场景都必须同时检查：

- **结果**：文件、退出码、状态或会话是否符合预期；
- **边界**：是否只在授权工作区和允许的执行后端内动作；
- **证据**：工具结果、审批绑定、checkpoint、Git diff 和审计链是否可核验。

`PASS` 只表示该场景的全部断言通过。Docker 不可用时测试可以 `SKIP`，但这只能报告为 `LIVE DOCKER NOT VERIFIED`，不能计入通过数。Fake executor 明确标记 `execution_simulated=true`，不能替代 Docker 证据。

## 3. 推荐验收命令

### 离线核心矩阵（无凭据、无网络）

```powershell
uv run pytest -q `
  tests/e2e/test_v01_acceptance_matrix.py `
  tests/e2e/test_fake_agent_workspace.py `
  tests/e2e/test_resume_demo_e2e.py `
  tests/integration/test_multi_turn_code_edit.py `
  tests/integration/test_chat_session_context.py `
  tests/integration/test_persistent_resume.py `
  tests/security/test_prompt_injection_agent.py `
  tests/security/test_path_escape.py `
  tests/unit/test_chat_cli.py
```

```powershell
uv run python scripts/resume_demo.py --backend fake --cleanup
```

该命令中的 process executor 是固定 fixture 校验器，输出必须包含 `SIMULATED`；它证明工作流、审批、恢复和证据链，不证明真实进程或容器隔离。

### Docker 现场验收

先确认 Docker Desktop、Linux containers 和配置中的固定镜像已就绪：

```powershell
uv run astercode doctor --root .
uv run python scripts/resume_demo.py --backend docker --cleanup
```

Docker 场景必须看到 `AsterCode resume demo: PASS`，并在 evidence JSON 中看到：

```json
{
  "execution_backend": "docker",
  "execution_simulated": false,
  "validation": {
    "sandbox": {
      "filesystem_sandbox": true,
      "network_sandbox": true,
      "host_workspace_read_only": true,
      "ephemeral_workspace_writable": true,
      "process_tree_containment": "docker_linux_container",
      "network_mode": "none"
    }
  }
}
```

容器超时后的清理由 `tests/integration/test_docker_process_live.py::test_live_docker_timeout_and_stop_leave_no_container` 单独验收；普通 `process.exec` evidence 不虚构一个未由 adapter 返回的 `container_cleanup_confirmed` 字段。Docker engine、固定镜像或 attestation 不可用时，pytest 的 `SKIP` 只能作为环境缺口记录；不得改成 fake 通过或手工编辑 evidence。

## 4. 第三阶段可靠性回归映射

第一阶段矩阵依赖下面的已有回归，不重复造一个会绕过宿主边界的测试。它们应和 AC-01–AC-10 一起运行；任何“模型说可以继续”都不能跳过这些状态检查。

| 可靠性风险 | 必须观察的行为 | 现有覆盖 |
| --- | --- | --- |
| 可重试 Provider/工具失败 | 只重试幂等且显式 `retryable` 的动作；未知副作用不自动重放；重试次数有上限并出现在事件/结果中 | `tests/integration/test_orchestrator.py::test_retry_is_limited_to_idempotent_retryable_calls`、`::test_provider_structure_retry_is_hard_capped_at_one`、`::test_retryable_provider_error_without_usage_fails_without_retry` |
| 陈旧 patch / 并发修改 | 上下文 hash 不匹配时不覆盖文件；多文件 patch 先全部 preflight；原文件内容保持不变 | `tests/unit/test_filesystem.py::test_patch_context_mismatch_does_not_overwrite_file`、`::test_multi_file_patch_preflights_all_context_before_writing` |
| 取消和 Ctrl-C | Provider/工具取消后清理任务；副作用边界未知时持久化 `unknown`，禁止假装完成或自动重试；进程树可回收 | `tests/integration/test_runtime_ctrl_c.py`、`tests/integration/test_artifact_output.py::test_cancelled_side_effect_handler_persists_unknown_before_propagating`、`tests/security/test_process_registry_kill.py::test_agent_process_is_persisted_and_cancelled_as_a_tree` |
| 超时 | 工具超时取 schema、运行预算和全局上限的最小值；输出管道和子进程收敛；Docker 超时不遗留容器 | `tests/integration/test_runtime_budgets.py::test_tool_timeout_is_minimum_of_spec_argument_and_run_budget`、`tests/unit/test_process_capture.py::test_exec_timeout_kills_descendant_that_inherits_pipes`、`tests/integration/test_docker_process_live.py::test_live_docker_timeout_and_stop_leave_no_container` |
| 上下文压缩 | 保留原始用户锚点、最近决策和必要工具证据；长度/字符数有上限，不把旧内部轮次无限带入新请求 | `tests/integration/test_chat_session_context.py::test_long_internal_turn_keeps_user_anchor_for_follow_up`、`tests/unit/test_orchestrator_compaction.py::test_conversation_compaction_keeps_user_turns_after_many_internal_decisions`、`::test_provider_context_bounds_repeated_tool_output` |
| Checkpoint/resume/reconcile | 新运行时只读取持久化 checkpoint；崩溃中断动作先只读 reconcile；恢复不能伪造、扩大或重复审批 | `tests/integration/test_persistent_resume.py::test_approval_resume_survives_new_runtime_instance`、`tests/integration/test_reconcile.py`、`tests/integration/test_chat_session_context.py::test_natural_language_cannot_overwrite_a_crash_interrupted_action` |
| 审批重放/状态漂移 | nonce、action hash、单次 lease 和文件 precondition 任一变化都拒绝；拒绝结果持久化 | `tests/security/test_gateway_single_use.py`、`tests/security/test_delete_preconditions.py`、`tests/integration/test_dry_run_session_grants.py` |

## 5. 失败分类和修复顺序

| 观察到的结果 | 含义 | 下一步 |
| --- | --- | --- |
| 核心 fake 场景失败 | v0.1 回归，不能发布演示 | 先修运行时/策略/测试，再重跑矩阵 |
| Docker 场景跳过 | 本机没有可验证 Docker 证据 | 启动 Docker 或记录 `LIVE DOCKER NOT VERIFIED`；不放宽策略 |
| Docker 场景失败 | 沙箱、清理或证据边界回归 | 检查 attestation、镜像 digest、网络和容器生命周期 |
| 真实 Provider/SSH/Browser 未运行 | 外部 live 能力未验证 | 保持 blocked；另开获批的 live smoke，不影响离线矩阵 |

## 6. v0.1 发布门槛

满足以下条件才可称为“v0.1 本地闭环”：

1. AC-01–AC-08 的离线测试全部 `PASS`；
2. AC-03/AC-04/AC-05 的 evidence 能在新进程中复核；
3. 至少在目标演示机器完成一次 AC-09 Docker `PASS`；若当前机器没有 Docker，只能标为候选而非完整发布；
4. `ruff`、`mypy`、完整 pytest、打包 smoke 和 portability preflight 均通过；
5. 报告明确列出跳过项、未验证 live 能力和未执行的外部副作用。

本矩阵不授权 commit、push、部署或连接真实主机。那些动作仍需单独的用户确认和对应的 live 证据。
